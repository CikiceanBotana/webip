# What webip detects

Every claim on this page is backed by output from one command against four live
sites. Nothing here is illustrative.

```bash
npm run scan -- --config config/showcase.json --out out/showcase
npm run examples -- out/showcase/findings.json
```

That run finished with `integrity.ok: true`, **zero scan errors** and every one
of the eleven checks completing on every page — which is what makes the
numbers below quotable at all. A run where a tool failed everywhere would look
exactly like a clean site, so `npm run examples` refuses to generate from one.

The four sites are `somnic`, `forkstead` and `maison-clair` on the
sogood.business platform, plus `cuddletherapyaz.com`, which is the same platform
on its own apex domain. They were chosen because their findings have been
checked by hand against the rendered pages — several were *disputed by the site
owner and turned out to be the tool's fault*, which is why the last section of
this page exists.

The JSON quoted below lives in [`docs/examples/`](./examples/) and is
regenerated by `npm run examples`, never edited by hand. If a rule stops firing,
that script fails loudly rather than quietly shipping a shorter page.

## 1. The answer comes first: `headline`

`findings.json` opens with a short list of what a visitor to the site would
actually notice. On the showcase run that is **five lines**, above 62 rules and
2,066 occurrences of evidence.

That ordering was not the original design, and the correction came from a site
owner who opened the file, met 770 rows, and could not find the four defects he
already knew about. Every one of those rows was true. None of them was the
answer. Three things were wrong:

- **Rules, not problems.** A trailing slash on a void element ranked beside
  "there is no navigation on a phone", because both are rules that fired.
- **One defect counted three times.** Faint text arrived as
  `contrast/contrast-over-image`, `axe-core/color-contrast` **and**
  `ibm-equal-access/text_contrast_sufficient` -- three rows, one thing to fix.
  They are now folded into one line, with every contributing rule listed under
  `rules` so the detail stays findable. When two engines disagree slightly
  (2.43:1 by pixel sampling, 2.45:1 by axe) that is corroboration, not two jobs.
- **No answer to "where".** An entry that cannot name the offending element is
  a slogan. `where` now carries the **visible text** -- `"Standard Session"`,
  `"How it works"`, `"Facut in Romania"` -- so the defect can be found by
  reading the page rather than by pasting a CSS path into devtools.

> [`examples/00-headline.json`](./examples/00-headline.json) — the whole answer,
> exactly as `findings.json` opens.

```jsonc
{
  "title": "Text is too faint to read against what is behind it",
  "severity": "serious",
  "sitesAffected": 4, "pagesAffected": 24, "occurrences": 181,
  "rules": ["axe-core/color-contrast", "contrast/contrast-over-image",
            "ibm-equal-access/text_contrast_sufficient", "lighthouse/color-contrast"],
  "where": [
    { "page": "https://cuddletherapyaz.com/services",
      "what": "Standard Session",
      "measured": "3.50:1 (rgb(139, 80, 64) on rgb(241, 178, 160), 20px)",
      "expected": "4.5:1" }
  ]
}
```

Two rules keep this list honest, and both were written after it printed
something useless:

1. **Only confirmed defects.** IBM equal-access reports `potentialviolation`
   results whose text literally reads *"Verify color is not used as the only
   visual means"*. That is the engine asking a human to look, not a defect it
   found, so those now land at `info` with a `-needs-review` suffix -- the
   convention axe already used for its own undecided results -- and never reach
   the headline.
2. **No line without a place to look.** If nothing in a theme can name an
   element, the line is dropped rather than printed. One such entry had pointed
   at `/html[1]/head[1]/link[7]` -- a stylesheet -- which is perfectly true and
   useless.

Everything filtered out is still in `issues` and `findings`, in full. The
headline reorders; it never discards.

## 2. Every finding is classified on four independent axes

A list of defects sorted only by severity is close to useless on a real site: a
trailing slash that affects nobody outrans a dead checkout link, because both
are "errors". So every finding carries four orthogonal classifications, and all
four are always set.

| Axis | Values | Answers |
| --- | --- | --- |
| `severity` | `critical` `serious` `moderate` `minor` `info` | How bad is it? |
| `category` | `accessibility` `markup` `links` `seo` `performance` `layout` `transport` `security` `scan` | What kind of problem is it? |
| `audience` | `visitor` `assistive-tech` `search` `developer` | **Who actually feels it?** |
| `lane` / `tool` | `http`/`browser`, and the engine that found it | Where did this come from? |

`audience` is the axis that makes the report usable. On one 357-site sweep,
**76% of all occurrences were developer-only spec deviations** — trailing
slashes, attribute casing, inline styles. They are real, they are worth fixing,
and they drowned 170 dead links. Filtering to `audience: "visitor"` turns a
5,000-row dump into a page of things a customer can actually see.

Getting that axis right takes more care than it looks. **"Accessibility" is not
a synonym for "screen reader."** A screen reader does not render colour at all,
so filing contrast, focus rings, tap targets and "click the green button"
instructions under `assistive-tech` hides them from the exact filter a site
owner reaches for. On a full 10-page pass that mistake moved **934 occurrences** into the
wrong bucket — the split went from `visitor: 206 / assistive-tech: 1437` to
`visitor: 1142 / assistive-tech: 503` once it was corrected — and among the
mislabelled was a hero paragraph at 1.97:1 that the site's own owner had
reported *because he could see it was faded*. A test now pins both directions.

`category` is deliberately not "which tool found it". axe, IBM equal-access and
Lighthouse all report contrast; a reader deciding what to fix does not care
which of the three spoke first, and the axis has to survive adding or removing
an engine.

### Standards are decoded from the vendors, not hand-written

Citing "WCAG SC 1.4.3" for 279 rules across three engines by hand would be a
table that silently rots on every upstream release. Instead each engine's own
metadata is decoded:

| Engine | Rules | Source of the mapping |
| --- | --- | --- |
| axe-core | 105 | its own tags — `wcag143` → `WCAG SC 1.4.3 (AA)` |
| IBM equal-access | 174 | `getRulesets()` → checkpoints carrying `num`, `name`, `wcagLevel` |
| Lighthouse (accessibility) | — | audit ids **are** axe rule ids, so the tags are read back off axe |
| our own rules | 39 | written out in `src/core/catalog.ts`, because no upstream doc exists |

That last row matters: rules we invented have no external documentation, so the
catalog carries their full `whatIsWrong` / `howToFix` / `standards` text rather
than a link to nowhere.

## 3. Navigation and the header

### `layout/no-mobile-navigation` — proved by clicking, not by guessing

> [`examples/01-navigation-missing.json`](./examples/01-navigation-missing.json)

The header hides its links below the `md` breakpoint and puts nothing in their
place. Every static check passes, because the links *are* in the markup — a
media query paints them out.

The check does not conclude this from class names. It surveys the header at a
desktop width, resizes to 390px, surveys again, then **finds every plausible
menu toggle and clicks them one at a time**, re-counting after each. "There is
no menu" is therefore a demonstrated fact rather than a failure to recognise
somebody's markup.

Three separate bugs in that clicking were caught by running it against
tailwindcss.com, getbootstrap.com, MDN, stripe.com, github.com, wikipedia.org
and news.ycombinator.com first — a generated CSS path that re-queried 5 toggles
into 17 elements, `HTMLElement.click()` being an untrusted event that framework
menus ignore, and the check's own search modal covering the real hamburger.
All seven control sites pass.

### `layout/mobile-navigation-cramped` — the nav is there, but it is the desktop nav

> [`examples/02-navigation-cramped.json`](./examples/02-navigation-cramped.json)

The harder half of the same question. The links survive at 390px, so the rule
above correctly stays quiet — but nothing adapted: the desktop row is simply
squeezed into a third of the width. Measured in **wrapped line counts and pixel
gaps**, so the finding says *"2 labels wrap onto a second line, and the logo
touches the first link at 0px"*, not "the nav looks bad".

## 4. Text you cannot read

### `contrast/contrast-over-image` — the answer no static engine will give

> [`examples/03-contrast-over-image.json`](./examples/03-contrast-over-image.json)

axe reports *"background color could not be determined due to a background
gradient"* and returns INCOMPLETE. IBM says *"verify the contrast against the
lightest and darkest colors of the background"*. Both are honest — neither can
resolve it statically — but on a site built on gradients that means the contrast
question goes unanswered exactly where it matters. On one 8-page site, **429
checks came back undecided.**

Static analysis fails here for three compounding reasons: Tailwind 4 emits
colours as `oklab()`, which no contrast engine parses; the text is
semi-transparent, so its rendered colour depends on what is behind it; and the
backdrop is a *stack* — a translucent veil, over a gradient, over a photograph —
that no single element owns.

So this check does not analyse. It renders, then looks: screenshot the page
twice, once normally and once with the glyphs made transparent, take **the
pixels that changed as the glyph mask**, and sample the real background under
the strokes. The result is a measured ratio at the worst point behind the text.

Two things this buys that are worth stating plainly:

- **It finds what the others miss.** A five-star rating built as five
  one-character `<span>★</span>` elements measured **1.20:1** on a green panel.
  axe, IBM and Lighthouse all stayed silent.
- **It refuses to overclaim.** The mask exists because a text node having a
  rectangle does not mean a glyph was painted in it. Without it, five of seven
  control sites lit up with SVG `<mask>` stencils, cards translated out of
  clipped carousels, and `opacity: 0` spans that exist only to measure a width.
  With it: github 3→0, wikipedia 1→0, stripe 28→7, tailwind 64→22 — and one
  heading dropped from a claimed 1.73:1 to passing, because no glyph had ever
  sat on the pixel that produced 1.73.

### `axe-core/color-contrast` — the same defect where static analysis is exact

> [`examples/04-contrast-static.json`](./examples/04-contrast-static.json)

Text on a solid background is the one contrast case static engines nail, so it
is left to them and deliberately not duplicated. Both engines agreeing is a
useful signal: the platform badge measures **2.43:1** by pixel sampling and
**2.45:1** by axe — two methods, one answer.

## 5. Screen readers

> [`examples/06-screen-reader.json`](./examples/06-screen-reader.json)

axe (105 rules) and IBM equal-access (174 rules) run on every page and cover
different ground — equal-access reports "potential" issues needing human
confirmation, which axe omits entirely. Everything they produce is classified
`audience: "assistive-tech"`, so it never competes with visitor-facing defects
for attention, and carries the WCAG success criterion decoded from the vendor's
own ruleset.

## 6. Layout and geometry

> [`examples/05-layout-overflow.json`](./examples/05-layout-overflow.json)

Rendered at 390px and again at desktop width. Horizontal overflow, elements past
the viewport edge, content clipped by its own container, and controls that
cannot be reached.

Geometry is the area where this tool has been wrong most often, so every
geometric rule now has to *demonstrate* its claim:

- Horizontal overflow is not inferred from `scrollWidth`. The probe calls
  `window.scrollTo(9999, 0)` and reads `window.scrollX` back — on the example
  page the answer is **197**, so the page really does pan sideways.
- "Blocked control" is answered by `document.elementFromPoint` at nine points
  across the control, **at every scroll offset**, because a `position: fixed`
  overlay covers what is under it only at the offset you happened to measure.
- Scrolling probes run **last**, because scrolling loads lazy images and fires
  reveal animations that would corrupt every rule above them.

## 7. Markup, links and transport

> [`examples/07-markup-invalid.json`](./examples/07-markup-invalid.json)

| Check | Engine |
| --- | --- |
| HTML spec conformance | W3C Nu validator (`vnu-jar`) and html-validate |
| Broken links | lychee, over every discovered URL |
| Transport | direct fetch: status, redirects, content type, `HEAD` vs `GET` |

The transport check earns its place: on the platform hub, **`HEAD /` returns 404
`application/json` while `GET /` returns 200 `text/html`**. Nothing that reads
the page will ever notice; every CDN cache, uptime monitor, link checker and
social preview crawler will.

Two batching decisions make this cheap rather than slow: the fast lane takes a
flat page list rather than a site, so a 357-homepage sweep is **one** JVM
process and one lychee invocation instead of 357 of each.

**A caveat that cost a false positive.** A link checker issues `GET`. A
`<form action="/api/waitlist">` is POST-only, so a GET returning 404 proves
nothing about it — form actions are now excluded, because 242 reported "broken
links" included several that were never links at all.

## 8. SEO, performance and branding

> [`examples/08-seo-meta-description.json`](./examples/08-seo-meta-description.json) ·
> [`examples/10-performance-lcp.json`](./examples/10-performance-lcp.json) ·
> [`examples/09-branding-favicon.json`](./examples/09-branding-favicon.json)

Titles, meta descriptions, canonicals, headings, Open Graph, structured data,
`robots.txt` and sitemap reachability from the fast lane; Core Web Vitals and
the four Lighthouse categories from the browser lane; favicons, touch icons and
logo/wordmark checks per site.

Performance numbers are reported at `info`. A Largest Contentful Paint of 3.1s
is a *measurement*, not yet a defect, and ranking it beside a hero nobody can
read would be dishonest.

**Page-level findings still carry an instance.** A metric has no element to
point at, but it does have a number, so its single instance describes the
document and puts `measured` / `expected` where every other finding keeps them.
"Which pages are over three seconds" is then a field comparison instead of a
regex over prose.

## 9. Is the run trustworthy?

Two mechanisms, both born from a real incident.

**`coverage`** records, per page and per tool, whether it completed, errored or
was skipped. Without it a page with no findings is ambiguous: perfectly clean,
or never examined? With it, a clean page is *provably* clean.

**`integrity.ok: false`** fires when a tool failed on *everything* it attempted.
Its silence then means "broken", not "clean", and the summary shouts it. This
exists because of a run where the Chromium processes were killed but the Node
parent survived: per-page error handling caught every navigation failure and
moved on, so the log kept incrementing `browser N/120 · 0 findings`. **A run
where every browser check fails looks identical to progress.**

`npm run examples` refuses to generate documentation from a run whose
`integrity.ok` is false.

## 10. What this tool deliberately does not claim

The most important section, and the one written last.

Nine reported "defects" were rejected on sight by someone who knew the site.
**Every rejection was correct.** The scan had measured accurately each time and
concluded wrongly, because a number was treated as a verdict:

| Reported | Reality |
| --- | --- |
| 72 tap targets below 24px | Conforming under SC 2.5.8's **spacing** exception — the links sat 47–110px apart |
| Content clipped by 40px | An `aria-hidden` decorative blur; the text ended 56px *above* the crop |
| 12 clipped card teasers | `-webkit-line-clamp: 2` — deliberate truncation, the design |
| A `<label>` cropped by 21px | `sr-only`: a 1×1 box with `clip-path: inset(50%)`. The clipping **is** the technique |
| 242 broken links | Included `<form action>` endpoints that only accept POST |
| 3 controls "blocked" by a badge | Two were clickable where they stood; the third was free 200px down the page |

Twice the failure ran the other way — a real defect the scan stayed **silent**
about — and both times a filter had discarded the evidence before anything was
measured. A `MIN_TEXT_LENGTH = 2` guard threw away fifteen one-character `★` at
1.20:1, and an ancestors-only backdrop walk threw away an entire hero at 1.97:1.

That second shape is the dangerous one, because **a silent check and a clean
page are indistinguishable in the output.** Every filter that drops evidence now
gets the same scepticism as every rule that emits one.

Three rules follow, and they govern every check in the codebase:

1. **Ask the browser; do not infer.** Click the thing, hit-test the point,
   scroll the page and read the offset back.
2. **A measurement is not a verdict.** Before adding a geometric check, work out
   what would make the number *not* a defect, and encode that first.
3. **Prove the negative on a control group.** Any rule that will fire across 357
   templated sites runs against seven well-built public sites first. That
   control group has caught eight false positives the target sites never would
   have.

The control group is for killing phantoms, not for demanding silence.
tailwindcss.com really does ship inline `lab()` code tokens at 2.71:1 on white,
and getbootstrap.com really does ship a 3.74:1 search placeholder. Both survive
because both recompute by hand.
